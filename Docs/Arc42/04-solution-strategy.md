# 4. Solution Strategy

*Part of the [Arc42 Architecture Documentation](README.md) - HRM System (Salary Grade Promotion).*

- **3-tier web architecture**, chosen so the UI, business logic, and data each evolve and scale independently: Angular SPA (presentation) → ASP.NET Core Web API (business logic) → SQL Server (persistence). See [Container Diagram](../c4/README.md#2-container-diagram) and [ADR-06](09-architecture-decisions.md#adr-06-technology-stack-angular--aspnet-core--sql-server).
- **Split the backend by business domain**, not by technical layer, at the component level: `Employee Management` and `Salary Management` are separate components so Salary Management can evolve (e.g. add Allowance Management later) without touching Employee Management. Supports the `#flexible` goal. See [Component Diagram](../c4/README.md#3-component-diagram) and [ADR-03](09-architecture-decisions.md#adr-03-split-the-backend-by-business-domain).
- **Inside Salary Management, use a classic layered pattern**: Controller → Service → Repository, so business rules (eligibility, approval, effective-dating) live in one place (the Service) instead of being scattered. Supports the `#suitable` goal. See [Code Diagram](../c4/README.md#4-code-diagram) and [ADR-04](09-architecture-decisions.md#adr-04-layered-design-inside-salary-management).
- **Never overwrite salary history**: every salary change is a new `HrEmployeeSalary` row with its own effective period, linked to the decision that caused it. Supports the `#secure` goal. See [ADR-02](09-architecture-decisions.md#adr-02-preserve-salary-history).
- **Separate "proposal" from "official record"**: a review result (`HrSalaryReviewEmployee`) is only a proposal and does not change any employee's real salary; only an issued `HrSalaryDecision` does. See [ADR-05](09-architecture-decisions.md#adr-05-separate-proposal-from-official-decision).
- **Support bulk operations at the API level**: endpoints accept batch requests (e.g. bulk-approve) and use server-side pagination, so the UI stays responsive with 150+ employees in a period. Supports the `#usable` goal. (Standard practice — no dedicated ADR.)
- **Expose standard operability hooks**: the Backend API provides a health-check endpoint and structured logging so it can be monitored and restarted safely in production. Supports the `#operable` goal. (Standard practice — no dedicated ADR.)
- **Authenticate and authorize by role**: HR Staff and Approver actions are restricted at the API layer, not just the UI. Supports the `#secure` goal. See [ADR-07](09-architecture-decisions.md#adr-07-authentication-and-authorization-mechanism).
