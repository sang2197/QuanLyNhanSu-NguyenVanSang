# 4. Solution Strategy

*Part of the [Arc42 Architecture Documentation](README.md) - HRM System.*

> **Status:** Current (auth: Proposed, health check: not implemented) · **Owner:** Sang2197 · **Last Reviewed:** 2026-09-18 · **Implementation Baseline Commit:** `77e5716`

- **3-tier web architecture**, chosen so the UI, business logic, and data each evolve and scale independently: React SPA (presentation) → ASP.NET Core Web API (business logic) → SQL Server (persistence). See [Container Diagram](../c4/README.md#2-container-diagram) and [ADR-08](09-architecture-decisions.md#adr-08-switch-frontend-framework-to-react) (frontend framework; backend/database chosen in [ADR-06](09-architecture-decisions.md#adr-06-technology-stack-angular--aspnet-core--sql-server)).
- **Split the backend by business domain**, not by technical layer, at the component level: `Employee Management`, `Organization Management`, `Salary Master Data`, and `Salary Grade Promotion` are four separate components so Salary Grade Promotion can evolve (e.g. add Allowance Management later) without touching the others; `Contract Management` is designed as a fifth component under the same rule but is not yet implemented. Supports the `#flexible` goal. See [Component Diagram](../c4/README.md#3-component-diagram) and [ADR-03](09-architecture-decisions.md#adr-03-split-the-backend-by-business-domain).
- **Inside every component, use a classic layered pattern**: Controller → Service → Repository, so business rules (eligibility, approval, effective-dating) live in one place (the Service) instead of being scattered. Interfaces are owned by the Application layer and implemented by Infrastructure; cross-domain access goes through another component's Service interface, never its repository. Supports the `#suitable` goal. Implemented for all four components. See [Class Diagram](../DetailedDesign/ClassDiagram.md) and [ADR-04](09-architecture-decisions.md#adr-04-layered-design-inside-each-backend-component).
- **Never overwrite salary history**: every salary change is a new `HrEmployeeSalary` row with its own effective period, linked to the decision that caused it. Supports the `#secure` goal. See [ADR-02](09-architecture-decisions.md#adr-02-preserve-salary-history).
- **Separate "proposal" from "official record"**: a review result (`HrSalaryReviewEmployee`) is only a proposal and does not change any employee's real salary; only an issued `HrSalaryDecision` does. See [ADR-05](09-architecture-decisions.md#adr-05-separate-proposal-from-official-decision).
- **Support bulk operations at the API level**: endpoints accept batch requests (e.g. bulk-approve) and use server-side pagination, so the UI stays responsive with 150+ employees in a period. Supports the `#usable` goal. Implemented (`bulk-approve`/`bulk-reject`, paged list endpoints). (Standard practice — no dedicated ADR.)
- **Expose standard operability hooks**: the Backend API is intended to provide a health-check endpoint and structured logging so it can be monitored and restarted safely in production. Supports the `#operable` goal. **Not yet implemented** — tracked as [DEBT-01](11-risks-and-technical-debt.md#technical-debt). (Standard practice — no dedicated ADR.)
- **Authenticate and authorize by role** *(Proposed — not implemented; the API currently has no authentication)*: HR Staff and Approver / Manager actions are to be restricted at the API layer, not just the UI. Supports the `#secure` goal. See [ADR-07](09-architecture-decisions.md#adr-07-authentication-and-authorization-mechanism).
